# 2026-10-21：无需人工开关的 USB 整芯片复位与恢复

## 结果与范围

在已连接的 PaperMono C153／ESP32-S3 rev v0.2（USB `303a:1001`、
序列号 `28:84:85:44:6D:A4`）上，已验证以下组合恢复路径：

**单连接清 FORCE_DOWNLOAD_BOOT + RTC watchdog 整芯片复位 → 按序列号重新枚举 →
提前开启 CDC 采集 → Espressif USB-JTAG `reset run` → 验证本次 TF/UI/BLE 启动。**

- 正常固件连续 **3/3** 通过，耗时 **15.20 / 15.18 / 15.19 秒**。
- 随后用最终版恢复工具，完成一次**写入正常镜像 + 自动 full 恢复**，进程退出 **0**。
- 恢复循环不刷 Flash、不清 NVS、不格式化 TF，无需用户按键或拔插。
  写入镜像那一步只擦写镜像覆盖的 Flash 扇区，不执行整片擦除。
- 已刷回随机 AP 凭据的正常镜像，不再保留临时固定 AP/路由器密码镜像。
- 这不是 PMIC 自身断电，也不代表 Wi-Fi 配网、HTTP、长期运行等产品验收全部通过。

## 一条命令恢复

需要 Python 3 + pyserial、esptool 5.3.1，以及**真正 Espressif OpenOCD**。
本机 Homebrew 和 Zephyr SDK bundled OpenOCD 不能替代该原生 USB-JTAG 包。

本次使用官方 `v0.12.0-esp32-20250422` macOS arm64 包，已核对官方工具清单 SHA-256：
`2cc39318d52f393233ff1f777871aebe5b97b3fbad29556a238489263401b774`。

```sh
export PAPERMONO_OPENOCD=/Volumes/extend/tmpwork/papermono-reset-tools/openocd-esp32/bin/openocd

# 仅复位/恢复，不写 Flash
python3 scripts/papermono_usb_recover.py --verify-only \
  --serial 28:84:85:44:6D:A4 --method full \
  --log /tmp/papermono-boot.log --reset-log /tmp/papermono-reset.log

# 明确提供镜像才会写 Flash，随后同样自动恢复并验证启动
python3 scripts/papermono_usb_recover.py --serial 28:84:85:44:6D:A4 \
  --log /tmp/papermono-boot.log build/zephyr/zephyr.bin
```

默认 `full` 是两个作用不同的复位，不是重试同一种复位：

1. esptool 在**同一连接**内执行：

   ```sh
   esptool --chip esp32s3 --port /dev/cu.usbmodem21201 \
     --before usb-reset --after watchdog-reset --no-stub \
     write-mem 0x6000812c 0 0x1
   ```

   清除强制下载标志，然后由 RTC watchdog 触发 whole-chip reset，重新采样 straps。
   不能把 WDT 寄存器配置拆成多个 esptool 连接：连接初始化会禁用 WDT。

2. 重新按序列号定位，开启串口观察，然后使用独立 JTAG USB 接口：

   ```sh
   "$PAPERMONO_OPENOCD" -f interface/esp_usb_jtag.cfg \
     -c 'adapter serial 28:84:85:44:6D:A4; set ESP_ONLYCPU 1; set ESP_FLASH_SIZE 0; set ESP_RTOS none' \
     -f target/esp32s3.cfg -c 'adapter speed 2000; gdb port disabled; tcl port disabled; telnet port disabled' \
     -c 'init; reset run; shutdown'
   ```

   此步骤使用 RTC 慢 RAM reset stub，复位数字域和相关外设；不是 Flash 编程，
   也不清 RTC controller。必须用对应版本的单核变量，避免探测未运行的 APP CPU；
   禁止自动 Flash 和 FreeRTOS 探测。复位完成即退出 OpenOCD，不让调试器常驻影响验收。

3. 工具要求本轮日志含 `pro cpu reset by JTAG`，其后再同时取得新 Zephyr boot、
   TF 挂载、LVGL 渲染和 BLE sync 就绪。不是见到任意驱动名就通过。

## 为什么过去会误判

本轮区分出至少两类状态：

- 刷写后直接 JTAG `reset run` 的一次试验返回 `boot:0x23 (DOWNLOAD...)`。
  普通 USB RTS 和 JTAG reset 均不重采 strap；RTC WDT 后锁存 strap 可变成 SPI boot。
- RTC watchdog 后，当前 Zephyr 镜像曾卡在 `_DoubleExceptionVector`：
  `PC=0x403743c0`、`EPC1=0x40385dfd`（时钟配置返回）、
  `DEPC=0x403740d5`（window-underflow handler）、`EXCCAUSE=0`。
  JTAG 当时能读内存和寄存器，证明执行已进入 Zephyr，不能说“主控没有电/没有复位”。
  随后 JTAG `reset run` 能正常启动；这个早期异常的具体机制仍待修复。

旧恢复脚本还有目标端口误绑定、忽略子进程失败、延迟后重新打开串口并清缓冲、
把普通启动与 power HIL PASS 混用等问题。已统一到
[共享恢复模块](<scripts/papermono_usb_reset.py>)、
[恢复 CLI](<scripts/papermono_usb_recover.py>)、
[采集 CLI](<scripts/papermono_usb_hil_capture.py>)。
[验收脚本](<scripts/papermono_acceptance.sh>)现在直接检查进程状态并传递目标序列号，
不再用管道匹配一个成功单词掩盖上游失败。完整验收脚本尚未在本轮从头执行。

新增 [恢复工具测试](<tests/host/test_usb_reset.py>) **15 项**，连同原有 25 组主机测试通过。
测试覆盖目标设备选择、错误码/超时、WDT fallback、JTAG 单核/序列号命令、
普通 boot/HIL 判据、新旧启动隔离、完整原始日志、观察先于复位，
以及设备初始未枚举、10 秒后唤醒的纯 HIL 捕获场景。

## 边界与仍需处理的问题

| 方法 | 重置范围 | 边界 |
| --- | --- | --- |
| 原生 USB RTS / hard-reset | core reset | 不等于外部 EN，不重采 straps |
| RTC watchdog | whole-chip/system reset | 本轮可触发；不能保证当前软件不再异常 |
| JTAG reset run | 数字域/外设，RTC controller 保留 | 不重采 straps；使用 RTC RAM stub |
| 本工具 full | RTC watchdog 后接可观察 JTAG 启动 | 已在该板/该镜像 3/3；不是所有故障的万能恢复 |
| M5PM1 timer POWERON + shutdown | 可安排 ESP 供电轨掉电再上电 | 官方支持的候选，本轮未实测；需要可运行 I²C 的 helper/应用 |

USB 未枚举、引脚或 USB 被应用关闭、物理 GPIO0 持续低、安全下载模式禁止寄存器写入时，
纯主机软件可能没有入口；不能承诺所有这些状态都能无人工救回。SoC reset 不会重启
always-on PMIC；M5PM1 进入 L0 后 PMIC/RTC 仍有电，不能称“整板完全断电”。

### 2026-10-22：应用正常但侧边红灯仍闪烁

SoC 恢复成功后，M5PM1 仍可能保留独立于应用灯控的红灯指示。本次实际在
应用关闭全部 RGB、寄存器回读为关闭时，红灯仍每秒闪烁；经 M5PM1 正常
重启命令 `0xA2` 后再次全关，用户确认灯已完全熄灭。该命令由可运行的
诊断固件在普通线程上下文发送，未修改 NVS 或 TF；当前 USB 恢复 CLI
不会发送它，也未在生产启动流程中加入无条件重启。

详细前后对照见[触摸板排查记录](touchpad-tuning-20261021.md)。应同时核对
运行时间、触摸和网络/HID 状态，不能把侧边红灯闪烁等同于内核挂起。

**ROM SHA-256 comparison failed 仍会出现在成功日志**；现镜像启动后继续执行。
这与刷写器核对写入内容不是同一个校验，不能写成“所有校验通过/全程零警告”。
本轮解决了自动恢复路径，未修复镜像 header/digest 或 RTC 冷启动异常的底层原因。

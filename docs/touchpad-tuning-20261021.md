# 触摸板起步与速度曲线调校

本次在用户已确认流畅的 `d379115` 上继续优化，保留该版本镜像作为回退。
不改变触摸轮询、页面布局、配对数据或 Wi-Fi 空节点保护。

## 调整

- 空闲后的首个有效位移直接排入工作队列，去掉之前固定 16 毫秒的合并等待。
  连续输入按 15 毫秒时间槽发送，后续采样不会推迟原有截止时间。
  时间槽在提交通知前预留；工作项再次检查间隔，覆盖输入线程抢占发送的情况。
  快速切换模式时，旧的延迟工作不能拖慢新模式首包。队列等待和无线连接间隔仍存在，
  不能将“无额外合并等待”解释为零端到端延迟。
- 指针超过 2 像素的起步抖动区即可开始跟随，点击取消门槛仍为超过 6 像素。
  轻微手指滚动允许移动少量指针后完成点击；已经超过点击门槛的滑动不会恢复成点击。
- 使用时间间隔计算移动速度，低速为 0.75 倍、高速上限 1.75 倍，中间连续过渡。
  两轴使用同一增益，保持斜向比例；整数报告保留有符号小数余量，细移不会持续丢失。
  重复坐标不更新时间基准，避免控制器重复采样让下一次位移被误判为高速。
  Mac 自身也可能应用加速，因此使用温和上限，最终手感由实机操作确认。
- 右侧滚轮继续按起点锁定区域、保留不足一格的余量，速度保持原有标定。

默认内部 DRAM 为 338808 / 399108 字节（84.89%，限制 85%），比上一版增加 16 字节。

该候选未通过实机验收：用户随后报告红蓝灯闪烁、系统卡死。JTAG 在约
293.8 秒处读到内核时间停止推进，`z_add_timeout()` 正在遍历自循环的
idle 线程 timeout 节点；中断嵌套计数为 `0xffffffff`。调用栈实际位于
FT6336 线程的 `k_msleep(8)`，而内核 current 指针却指向 idle，说明调度

启动窗口检查不能作为长期稳定性结论。下一候选保护 HAL 中断回调中的
`k_yield()` 调用：蓝牙适配器与无线共存适配器的中断唤醒交给内核在中断
退出时调度，普通线程调用仍保留原有行为。重定向仅作用于这两个源文件，
函数与计数器位于内部 RAM，不在无线中断中记录日志。HAL 与 Zephyr 工作树
中的其他修改保持原样。此调用违反 Zephyr API 的线程上下文要求，但还需
通过实机路径确认与本次挂起的因果关系，不能仅凭静态发现宣布根因已解决。

主机测试编译真实兼容规则与保护函数，分别验证 ESP32-S3/C3 两种配置：
线程调用正常进入调度器，中断调用不进入调度器，别的源文件不受宏重定向影响。
默认、局刷和自检构建均通过，默认 DRAM 为 338864 / 399108 字节（84.91%）。
后续运行观察与用户手感验收另行记录。

## 中断退出竞态

第一轮中断 yield 保护候选仍在 382.283 秒出现 CPU 指令取址异常，异常栈
属于 FT6336，而 current 仍指向 idle。无线 yield 拦截计数为 0，鼠标报告
为 0，蓝牙接收栈剩余 476 字节、中断栈剩余 960 字节，不能将该保护称为
本次挂起的根因修复。此次运行没有连接调试器，也没有触摸输入。

进一步核对当前 SDK 的 `CROSS_STACK_CALL`，发现 C 中断处理完成后，
`retw` 已经切回被中断线程的栈，随后才屏蔽中断。蓝牙三级中断若恰好到达
这个边界，会覆盖仍被调度器引用的保存帧。再次恢复旧帧可能重复经过中断
退出尾部，造成嵌套计数下溢、陈旧线程上下文恢复、死循环或栈归属错误。
两次本机现场均与此机制吻合；外部也有同平台的
[退出侧修补与故障分析](https://github.com/soghoyan/zephyr/commit/2a527c5703d9366efbeba3a84efe45bf8d183b8d)。

在构建目录生成 SDK 汇编头文件的兼容副本，将已有的 `rsil` 移到
`CONFIG_USERSPACE` 条件外，使非用户态配置也在离开中断栈前屏蔽中断。
正常上下文恢复仍使用保存的 PS，不禁用正常运行时的中断嵌套。
SDK 源文件保持原样，只有 Xtensa 内核目标优先使用该副本；已修复的 SDK
直接使用原文件，无法识别的版本会在配置阶段报错，避免静默漏掉修补。

主机测试覆盖用户态开关、生成头文件的优先级、已修复 SDK 和未知 SDK。
目标反汇编确认实际指令顺序为 `callx4`、保存返回值、`rsil a6, 6`、`retw`。
后续实机结果单独记录，不能用前一候选超过五分钟的短期通过作为验收。

## 2026-10-22：红灯独立闪烁的实机区分

在相同内核修补上临时加入灯控寄存器回读，运行在已有系统工作队列，未改变
触摸、HID 或配对配置。connected 状态下实际读到 M5PM1 电源配置 `0x07`、
LED 驱动配置 `0x00`，蓝绿 PWM 均为 `0x8333`，频率为 5000 Hz：红灯已被
应用关闭，蓝绿为约 20% 占空比。应用没有周期性切换红蓝的指令。

受控熄灯试验中，红灯关闭、蓝绿 PWM 均为 `0x0000`，用户仍观察到红灯
每秒闪烁。随后只通过 M5PM1 发出正常重启命令 `0xA2`；USB 重新枚举，
PMIC 报告命令复位唤醒标志 `0x10`，系统重新完成 TF、UI 和 BLE 启动。

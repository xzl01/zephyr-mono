# 2026-10-20 TF 卡首次打通记录

本记录说明 C153 的 TF 卡在这台设备上从未工作成功的根因、修复和实机验证结果。

## 根因：板级 pinctrl 把 SD 的 CLK 与 CMD 接反

`boards/m5stack/m5stack_papermono/m5stack_papermono-pinctrl.dtsi` 的
`sdhc0_default` 把两条关键信号写反了：

| 信号 | 板级实际（M5Stack 官方 UserDemo） | 修复前 DTS | 修复后 DTS |
| --- | --- | --- | --- |
| CLK | GPIO13 | GPIO12 | GPIO13 |
| CMD | GPIO12 | GPIO13 | GPIO12 |
| D0..D3 | GPIO11..GPIO8 | 一致 | 一致 |

依据是 M5Stack 官方 `M5PaperMono-UserDemo` 的 `main/hal/hal_tf_card.cpp`：
`TF_CLK_PIN = GPIO_NUM_13`、`TF_CMD_PIN = GPIO_NUM_12`、
`TF_DATA0..3 = GPIO_NUM_11..8`。TF 供电 `TF_EN_PIN = M5IOE1_PIN_14` 与
卡检测 `TF_DET_PIN = M5IOE1_PIN_1` 在该枚举里是从 1 开始编号，对应 Zephyr
`&m5ioe1` 的 0 基索引 13 和 0，与本仓库 DTS 一致，无需改动。

CLK/CMD 接反的后果是卡完全收不到时钟：主机侧每条命令都以控制器超时结束
（`CMD8`/`CMD55` 返回 `-116`，`sdhc` 记录 `error = 0x107`），
`sd_init()` 无法识别卡类型，最终返回 `-ENOTSUP`（`-134`）。这解释了此前
"`Card never left busy state` / `-134`" 以及所有内容功能不可用的现象。

## 第二个问题：卡片是 GPT 分区表，Elm FATFS 无法挂载

修好引脚后卡能被正常识别（4-bit、20 MHz、HS 时序），但 `fs_mount()` 返回
`-ENODEV`。直接读 LBA0 得到 `sig=55aa part0_type=ee part0_lba=1`，即
**保护性 MBR + GPT**。Zephyr 的 Elm FATFS 只认 MBR 上的 FAT 分区或整盘
（super-floppy）FAT，因此需要把卡重新格式化为 FAT。

新增能力：

- `papermono_content_store_format()`：以 `FS_FATFS` + `FM_SFD` 建 super-floppy
  FAT（无 MBR），随后重新挂载。
- `CONFIG_PAPERMONO_TF_FORMAT_WHEN_UNFORMATTED`（默认 **n**，破坏性）：
  仅用于首次配置已知空白卡，配套 `tf_format_hil.conf` 显式 opt-in，
  与项目既有的 `power_*_hil.conf` 高风险动作约定一致。
- 挂载失败时把 `-ENODEV` 正确归类为 `PAPERMONO_MEDIA_UNFORMATTED`，
  不再混入 `PAPERMONO_MEDIA_ERROR`。

## 实机验证（USB 串口日志，2026-10-20）

格式化（已获操作者确认，卡内无重要数据）：

```text
TF detect initialized: inserted=1
fs: fs mount error (-19)
TF card has no usable filesystem; formatting (opt-in)
TF card formatted; all previous content was erased
TF content store mounted at /SD:
Organizer loaded: events=0 tasks=0 notes=0 error=0
```

驱动自检（`driver_selftest.conf` 镜像）确认了 FAT 读写闭环：

```text
HIL microSD detect raw=0 inserted=1
HIL microSD ready: 124735488 sectors x 512 bytes
HIL microSD check passed
HIL microSD FAT write ok: 20 bytes
HIL microSD FAT read back and verified
HIL microSD FAT check passed
```

`124735488 x 512` 约合 63.9 GB，与本机插入的 64 GB 卡一致。写入使用临时文件
`/SD:/papermono/.selftest.tmp`，读取比对后即删除，不残留内容。

## 顺带修复

- `ensure_directory()` 先 `fs_stat()` 再 `fs_mkdir()`：原来每次挂载都会因已存在
  的目录打印十条 `failed to create directory (-17)`；现在只在确实缺失时创建。
- `ui_failure_streak` 只在交互式构建中使用，非交互 profile（自检/演示）编译时
  用 `CONFIG_PAPERMONO_INTERACTIVE_UI` 包住，消除 `-Wunused-variable`。

## 未闭环

- 内容中心 HTTP 上传尚未在实机上做端到端验证（需要先连接 SoftAP 并配对）。
- SoftAP 首次启用后会多一次 "disable + 500 ms 重试"，随后验证通过；功能正常但
  该自愈动作值得单独收敛。
- 长时间连续读写、热插拔、断电后的一致性仍需耐久验收。

## 内容导入事务的实机验证（2026-10-20 补充）

在 `driver_selftest.conf` 镜像中新增了内容导入事务检查，覆盖 HTTP 上传在
拿到请求体长度之后走的同一条存储路径（`import_begin` → `import_write` →
`import_commit` 校验并原子替换 → 通过公开的 open 路径回读 → 删除）：

```text
HIL microSD FAT write ok: 20 bytes
HIL microSD FAT read back and verified
HIL microSD FAT check passed
HIL content import committed and read back
HIL content import transaction cleaned up
HIL content import check passed
```

尚未覆盖的是 HTTP 报头解析（`Content-Length` 捕获）与网络可达性：本机 macOS
的 Wi-Fi 主动扫描被系统限制（`airportd` 返回 `-528350195`，`networksetup` 报
"Could not find network"），无法从开发机连上设备 SoftAP。这部分需要手机或
另一台电脑按产品实际流程连接 `PaperMono-XXXXXXXX` 后验证。

## 设备内的格式化入口（2026-10-20 补充）

新卡通常是 exFAT 或 GPT 分区，插上后无法直接使用。此前只能通过 opt-in HIL
镜像格式化，现在设备本身提供入口：

- 系统状态页的「存储」区在 `PAPERMONO_MEDIA_UNFORMATTED` 时显示
  「格式化 TF 卡」按钮，页脚提示「轻触格式化 · 会删除卡内全部文件」。
- 轻触进入与休眠/关机共用的确认页，标题「格式化 TF 卡？」、正文说明会删除
  全部分区与文件且不可撤销，取消返回系统状态页。
- 确认后调用 `papermono_content_store_format()`，成功后请求内容刷新；失败则
  在系统状态页显示「格式化失败」而不是静默忽略。
- 仅在检测到卡已插入且没有可挂载文件系统时提供该入口；卡正常或未插卡时不显示，
  避免误触。

命中区域 `system_storage_rect` 与渲染共用 `include/papermono/ui_layout.h`，
并有主机测试保证它在屏幕内、不越过底部导航、且不与状态行重叠。

验证边界：格式化函数本身已在实机完成（见上文）；本入口的实机点击流程需要屏幕
交互，尚未由本机自动化验证。

## 内容中心 HTTP 端到端验证：两次尝试与结论（2026-10-20）

内容中心 HTTP 上传是全项目最后一项未在实机闭环的验证。本轮尝试了两条自动化路径，
均受环境限制，结论记录如下，避免后续重复投入。

### 尝试一：开发机连接设备 SoftAP

设备 AP 正常广播（`system_profiler` 可见 `PaperMono-XXXXXXXX`，信道 6），但开发机
macOS 拒绝关联：

```text
airportd: Failed to perform Wi-Fi scan, returned error -528350195
networksetup -setairportnetwork en1 <ssid> <psk>  →  Could not find network
```

已排除 Internet Sharing / AP 模式占用（`ap1`、`bridge0` 均 inactive）、已尝试
关机重开 Wi-Fi、已把目标网络加入首选列表，结果一致。属于 macOS 对 SSID 扫描/关联的
权限限制，无法在无人值守环境绕过。

### 尝试二：设备内 loopback 自检

新增一个 opt-in 自检镜像，在内容中心启动后通过 `127.0.0.1:80` 调用真实 HTTP API
（配对 → 兑换 ticket → 带 `Content-Length` 上传 → 列表 → 空 body 拒绝 → 删除）。

结果：`CONFIG_NET_LOOPBACK=y` 后 loopback 接口存在且已 up（`iface=lo up=1`，
`127.0.0.1` 已注册），但 `connect()` 返回 **-120 (EHOSTDOWN)**；显式把 socket
绑定到 `127.0.0.1` 作为源地址后仍然相同。结论：该 Zephyr 配置下 loopback 无法把
APSTA 实例的报文自投递到本机监听端口。相关代码已全部移除，未留在固件中。

### 结论

HTTP 上传端到端验证**必须**由一台能连上 SoftAP 的设备（手机或电脑）完成。设备侧
可验证的部分（FAT 读写、内容导入事务、内容中心接口契约的主机测试）均已通过；剩下
的仅是「HTTP 报头 → 存储」这段在真实网络下的联调。
